Session 3 — The Pipeline: Single Path to Production

Green means deployable.

Set the frame and objectives. By the end they can: (1) treat the pipeline as the SOLE path to every shared environment; (2) express "deployable" as automated criteria, not a meeting; (3) build one immutable artifact and promote the SAME bytes dev → qa → prod; (4) design fast, safe recovery on AWS — fail forward first, roll back when it's costly; (5) write their team's phased migration plan. The one-line arc of the course: Session 1 was the WHY (small batches, the minimums), Session 2 was the first PRACTICE (trunk-based dev, flags, CI) — today is the SYSTEM those two make possible. Keep the course refrain: this is about HOW we deliver, independent of platform; the new AWS services are just where it's cheapest to establish.

You have a deployable trunk — what carries it to prod?

60-second recap only — don't re-teach Sessions 1–2. Small batches, daily integration, flags and CI gates gave us a trunk that is ALWAYS DEPLOYABLE. Then the connect: have each person name, out loud, how a change reaches prod on THEIR stack today — and notice the two shapes. NEW cloud-native services (our iac-baseline): deploy straight from trunk — dev auto on green, qa and prod behind manual gates. No extra branch. ESTABLISHED .NET apps on Azure VMs (verified against ciranet-attorney-api's shared dotnet ci-template): dev ALSO auto-deploys from trunk, BUT qa and prod deploy from a release/YY.M.W branch cut WEEKLY by a scheduled job — qa auto on that branch, prod a manual rolling wave deploy across the app servers. A week of commits pile into it and cherry-picks are routine. (There's also a demo env, omitted here.) THE POINT: that release branch is exactly the long-lived branch Session 2 told us to retire — weekly batching and cherry-picks are its cost. Session 3 is about collapsing to a single path from trunk. Release manager: for the older apps a release manager owns cutting and curating that weekly release — mention it, but it's not the burden; the branch is. Don't fix anything yet; just surface it so the "pipeline decides releasability" slide lands on their own process. Name the running example once: the HOA VIOLATIONS API — a TypeScript Lambda behind API Gateway that records a violation to DynamoDB and publishes a ViolationRecorded event to SNS. Every slide today is grounded in that one service.

Flags aren't free

Default: no flag

  • Behavior change → branch by abstraction
  • New feature, nothing calls it yet → keystone: wire it up last
  • New API route → build it, expose it last
  • Bug fix / simple change → just deploy

A flag earns its keep when

  • Gradual rollout or test-in-prod → dark launch
  • Testing in qa → keeps the path to prod unblocked
  • Different behavior per customer
  • An experiment — A/B test
  • Cross-team / cross-service coordination
full decision tree → beyond.minimumcd.org/docs/migrate-to-cd/optimize/feature-flags
Callback to the Session 2 decision — flag / branch-by-abstraction / ship. You CAN merge dark behind a flag, but reach for it last, not first. A flag is code and config you carry in every environment until you remove it — and most teams never do: a flag roughly doubles the test burden, flags nest into combinatorial state, and a Release toggle no one removes is flag debt. Cheaper mechanisms keep the trunk deployable without that tax: branch by abstraction for a behavior change; the keystone pattern for a brand-new feature — merge it daily but reachable only from its own tests, then wire in the real entry point as the last commit; build a new route and expose it last; for a bug fix, just deploy. Reserve the flag for genuine gradual rollout, test-in-prod, per-customer behavior, an experiment, cross-team coordination, or to test a change in a shared qa without blocking the path to prod — merge it dark, so held-back work never stalls a prod fix. Full decision tree is the beyond.minimumCD link on the slide. Note the tension with later today: when a flag IS warranted, it's also your fastest recovery lever — flip it off, no deploy. Powerful, but not free.

When the trunk isn't deployable

big batches + a red trunk = you can't ship when it matters most
Tell it blameless — no names, no team. Recently, on one of our services: two large changes were both in flight, both merged to main, and both had issues. Before either was sorted, a production problem surfaced. The fix itself was a one-liner — but it couldn't go out, because the pipeline ships the TRUNK, and the trunk now carried two broken changes that wouldn't go green. The small fix was trapped behind big broken batches. This is the whole case for what Sessions 1–2 asked for: small batches, stop-the-line when the build is red (CI minimum #5), new work doesn't break delivered work (#6), and a trunk you keep deployable at ALL times — not for tidiness, but because the day you need to ship in a hurry is the day you can't afford a red trunk. This is exactly what today's single-path pipeline is built to protect. Then move to Part 1.
Part 1 of 3

The Single Path & Its Verdict

One line: "Two ideas do the heavy lifting — there is exactly ONE way in, and the pipeline, not a meeting, decides what's deployable." Move to the next slide.

One path to shared environments — no side doors

The minimum (#2): every change to a SHARED environment goes through the pipeline — no "just this once" sam deploy from a laptop to qa. Three reasons it's non-negotiable. REPRODUCIBILITY: every shared-env change has the same provenance — a commit, a pipeline run, an audit trail. SECURITY: deploy permissions live with the pipeline via GitLab OIDC — short-lived, per-environment role assumption, NO static AWS keys anywhere. TRUST: if there's exactly one path, the pipeline's verdict can MEAN something — which is the whole next slide. The escape valve that keeps this liveable: PERSONAL SANDBOX STACKS (dev-aws-violations-api-<username>) are yours to sam deploy to and break freely — they're not shared, so they don't need the pipeline. Everything SHARED does. AI note, one line: when an agent can emit a fix in seconds, the temptation to hot-fix straight to prod is STRONGER — that shortcut is exactly the side door this rule forbids.

The pipeline decides releasability

Continuous Delivery — deployable on demand; a human picks the moment Continuous Deployment — every green commit auto-ships (keep them distinct)
This is the minimum most teams haven't fully reached. Our own baseline now auto-promotes dev on green, but qa and prod are still when: manual, so the pipeline doesn't yet own the release verdict. The shift: GREEN SHOULD MEAN DEPLOYABLE, and the pipeline should say so without a meeting. A human may still choose WHEN prod happens — that's Continuous DELIVERY, not Continuous DEPLOYMENT, and the distinction matters — but they're approving TIMING, not re-deciding READINESS the pipeline already proved. The tell that you're not there yet: a meeting decides whether the build is "ready." In the target pipeline you'll read later, dev and qa AUTO-PROMOTE on green and only prod keeps a gate. ENGINEERING-LEAD NOTE (say it, keep it honest): a manual prod gate can be a LEGITIMATE, PERMANENT control — compliance, or early confidence in a new service — distinct from a DEBT gate that just re-litigates readiness the pipeline already proved. Keep the legitimate ones, name them as timing decisions, and remove the rest as trust grows. IF ASKED "I gate qa so auto-deploys don't clobber my manual testing" — that's real, but it's an ISOLATION gap, not a control: keep other work dark behind flags so it doesn't change the surface under test, and use an ephemeral env per change where the deploy itself disrupts (a Lambda alias shift is invisible; a CloudFront converge isn't). The gate's hidden cost is batching — green work queues behind it. Fix the isolation; don't enshrine the gate. And the stop-the-line rule from Session 2 now extends past the build to the DEPLOYMENT PIPELINE: a red pipeline is the team's #1 priority — no new feature work until it's green (minimum #6).

"Deployable" is automated criteria, not a meeting

when the automated checks don't exist yet → manual verification gates the flag flip (release), not the merge
"Deployable" is exactly the set of checks the pipeline runs — for the Violations API: lint clean, unit tests pass, coverage at or above the team floor, IaC valid, security scan clean. These are the validate / test / security stages you already met in Session 2's CI file — the FRONT HALF of the full pipeline. The discipline in one line: IF IT ISN'T GATED AUTOMATICALLY, IT ISN'T PART OF YOUR DEFINITION OF DEPLOYABLE — it's a hope. Now the honest brownfield case — true across much of our estate: when those automated checks don't exist yet, manual verification does NOT vanish, but it stays OUTSIDE the automated definition of deployable — it gates the RELEASE (the feature-flag flip), never the merge. Make it an explicit, owned step, not a side-channel sign-off, and automate it down over time by adding tests where you change code. AI note: two cautions live right here. COVERAGE is a SMOKE ALARM, not a target — when the same agent writes the code and its tests it will hit the number and verify nothing; tests must pin INTENT, confirmed INDEPENDENTLY. And add a DEPENDENCY-PROVENANCE / lockfile-integrity check once an agent is editing package.json — hallucinated package names are a real supply-chain hole.

Two decisions, two owners — communicate the release

Session 2 taught deploy ≠ release; here's what it does to OWNERSHIP and COMMUNICATION. The prod DEPLOY gate (if you keep one) is an ENGINEERING AUTHORIZATION — owned by the Engineering Lead: is this safe to put in prod now. The RELEASE — the flag flip users actually feel — is a separate decision about WHICH feature goes live WHEN and to WHOM, owned by whoever runs release comms and flag governance (our evolved RELEASE-MANAGER role), with the business. Two decisions, two owners, often two different days. And it moves COMMUNICATION: you announce the RELEASE, not the deploy — the weekly client email doesn't die, it gets REBUILT FROM USER-FACING RELEASES instead of the deploy log. That's why the target pipeline runs one merge-request-time job, release-impact-label, that forces every change to declare customer-facing (with a note) or no-user-impact before merge — so release notes have a reliable source. Pointer: resources/communicating-releases.md.
Part 2 of 3

Build Once, Promote the Same Bytes

One line: "The verdict only means something if the thing you tested is the thing you ship — so build the artifact once and promote the SAME bytes." Move to the next slide.

Build once · promote the same bytes

Build the Lambda bundle ONCE, from one commit, then promote the IDENTICAL artifact through dev → qa → prod — never rebuild per environment. Why it matters: IF YOU REBUILD FOR PROD, YOU'VE DEPLOYED SOMETHING YOU NEVER TESTED. "Works in qa, breaks in prod" is almost always a rebuild, or config baked into the build. For SAM specifically: sam build then sam package uploads the code to an artifact bucket and emits a PACKAGED TEMPLATE referencing it by a CONTENT HASH; each environment's sam deploy consumes that SAME packaged template. Two keys, same bytes: CI_COMMIT_SHA labels the pipeline artifact so YOU can find and redeploy it; the content hash is how CLOUDFORMATION knows the bytes are unchanged. MULTI-ACCOUNT NOTE (common at RealManage): if dev/qa/prod are separate AWS accounts, the artifact bucket must be readable across accounts — a shared artifacts account or a cross-account bucket policy — so each stage promotes the same bytes. Rebuilding per account silently breaks the guarantee. This immutable, stored artifact is also what makes rollback real in Part 3 — "the last good version" is a thing you can redeploy, not a memory of what main used to be.

Config travels with the artifact

Environment differences live in configuration/{dev,qa,prod}.config (the iac-baseline convention) and arrive as SAM parameters — NOT hand-patched into a running Lambda. The artifact is identical across environments; only the config APPLIED AT DEPLOY differs: table names, log levels, SNS topic ARNs — and FLAG VALUES. Secrets are never in config files — they're REFERENCES to SSM Parameter Store / Secrets Manager ARNs. Here's the payoff that ties back to Session 2: because a FLAG'S VALUE IS CONFIG, not baked into the immutable artifact, the SAME BYTES run flag-ON in qa and flag-OFF in prod — which is exactly what lets you test in qa while the change is already deployed DARK to prod, then flip prod to release. Immutable artifact (#5) + config-with-the-artifact (#9) are what make deploy ≠ release mechanically true.

Read the artifact's contract

Parameters carry the only per-environment differences — the bytes don't change Flags default off — the artifact ships dark; a flip (config) releases it Canary + alias is the rollback machinery we build on in Part 3

→ examples/violations-api/template.yaml

Frame, then open the file. Three things to land at the editor. (1) The Parameters block is where environment differences arrive — EnvironmentName, LogLevel, the two flags — and the comment says it out loud: the artifact is identical; only these change. (2) FlagViolationsRecord / FlagViolationsNotify default to "false" — the artifact ships DARK, and a flag flip (config), not a deploy, releases it — the mechanical cash-out of the last slide. (3) AutoPublishAlias: live plus DeploymentPreference: Canary10Percent5Minutes with a CloudWatch error ALARM — that's the ROLLBACK MACHINERY we build on in Part 3; every deploy creates an immutable version and shifts traffic gradually. Point out briefly that the alarm watches the ERROR RATE of the live alias, not a raw count — a threshold of 1 error would roll back a healthy deploy on a single stray error, and a canary over an idle window verifies nothing (missing data reads as OK). The canary is only as strong as the traffic during its window. Keep this file open next to Session 3's .gitlab-ci.yml in the workshop.
Part 3 of 3

Production-Like Environments & Recovery

One line: "Green only means something if it's green somewhere that looks like prod — and even then, things break, so the last thing we build is how we recover." Move to the next slide.

A production-like environment

The closer qa is to prod, the more a green qa means. divergence is where "passed qa, broke in prod" is born
Keep this short — it's a 5-minute beat. Our qa mirrors prod's SHAPE via configuration/qa.config: same resource types, same topology, smaller scale (you saw it in the template's Mappings — log retention 7 / 30 / 365 days for dev / qa / prod). The principle is simple and unforgiving: THE CLOSER QA IS TO PROD, THE MORE A GREEN QA MEANS SOMETHING. Divergence between qa and prod is exactly where "passed qa, broke in prod" is born — and it's the other half of the same guarantee as build-once: same bytes, prod-like shape.

Fail forward — the default

The whole point of the pipeline is that shipping is now small, fast, and safe — and that changes your DEFAULT when prod misbehaves. FAIL FORWARD: diagnose, reproduce it with a fast unit test (which now also guards the regression from returning), ship a small fix MR, and let the same canary-verified pipeline carry it to prod in minutes. Why this is usually right: a forward fix SOLVES the problem — a rollback only DEFERS it, you still have to fix and re-ship; it's safe by the same logic as any deploy (small batch, tests, canary); and it sidesteps the data trap on the next slide. The genuinely fastest mitigation, when the bad behavior is behind a FEATURE FLAG, is to flip it off — no deploy at all — then fix forward behind the flag at a calm pace. AI note, one line: an agent produces the forward fix in minutes, which makes fail-forward MORE clearly right — but the fix needs the SAME GATES as any change; the incident is the most tempting, and most dangerous, place to let unreviewed work skip the pipeline.

Roll back — the emergency lever

→ examples/rollback-on-aws.md

Minimum #8 still requires you to HAVE fast, rehearsed rollback — it's the emergency lever, not the reflex. Reach for it only when BOTH are true: COSTLY (users, the board, data, revenue, or compliance being harmed right now) AND TIME-SENSITIVE (a forward fix won't land fast enough). Then roll back to stop the bleeding, and fail forward once the pressure's off. At the editor, walk the file: OUR ROLLBACK is re-running the last known-good deployment in GitLab — because every artifact is immutable and stored (tagged by CI_COMMIT_SHA, kept 30 days), that's a REDEPLOY of the previous good build through the same pipeline, not a rebuild — NEVER a hand-edited Lambda alias, which bypasses the pipeline (#2) and drifts from IaC. Behind it: canary auto-rollback (the template.yaml DeploymentPreference from slide 9), CloudFormation auto-rollback for failed updates, and the flag kill-switch. The trap to burn in: ROLLING CODE BACK DOES NOT ROLL DATA BACK — if the bad version already wrote a new DynamoDB shape or emitted an SNS event, reverting code strands you on data the old code can't read; that's why changes stay backward-compatible (EXPAND/CONTRACT), and once state has moved, failing forward is often the only safe option. Close with the rule: REHEARSE IT IN QA — deploy a deliberately broken version, practice and TIME both the fail-forward loop and each rollback move. A recovery move you've never run is a hope, not a capability — only then does #8 count as met.

The database is no exception · bonus

Worked end-to-end with DbUp — a deliberate C#/.NET example (the schema estate lives in .NET) the end-state — automation-only schema, no standing DDL — is owned by DX
Time-permitting bonus — the database is not a special case. The PIPELINE IS THE ONLY WAY to change a shared database (#2). The MIGRATION RUNNER IS AN IMMUTABLE ARTIFACT built once and promoted — the same scripts run against dev → qa → prod, varying only the connection string (#5). And recovery is FORWARD-ONLY: a bad migration is fixed by a new FORWARD script plus expand/contract, NEVER a hand-edit on a shared database — the exact analog of fail-forward for code. The end-state we're driving toward: schema and baseline data change ONLY through automation, local databases as the playground, no standing human DDL on shared environments — and DX OWNS THAT PATH; here we just make the mechanism concrete. Worked end to end in the DbUp example (C# on purpose — the schema estate lives in .NET; one of the course's two deliberate non-TypeScript examples). Pointer: resources/database-delivery.md.
