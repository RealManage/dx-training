## What changed since Round 2 — the three themes, attacked from my lens

### Theme 1 — Database delivery (the hardest case for my skepticism)

The course now wants schema changes shipped through the pipeline to a *shared* database, daily, no long branch, no hand-edits. That is the most aggressive thing CD has asked of me in three rounds, and it is precisely where I expected "trunk-based is chaos" to bite hardest. Verdict: **mostly convinced — sufficient, with one fear it bounds rather than eliminates.**

What earned it:

- **It refuses to pretend the database is just more code.** `resources/database-delivery.md:8` names it outright — "The database is usually *the* reason small batches feel impossible." A course that opened by waving that away would have lost me on line one. It doesn't.
- **The forward-only + expand/contract recovery story is coherent and I can't poke a hole in the logic.** The fear is "bad schema deploy to shared prod, now what — there's no down-button." The answer (`database-delivery.md:56-60`, `db-migrations/README.md:37-39`): there is *deliberately* no down-button, because a down-migration on a shared DB with live data is the actual foot-gun. Reversibility comes from *every step being backward-compatible* (expand/contract) so the **application** rolls back independently of the schema, plus a new forward fix-migration for the schema itself. The `Script0002__expand_add_due_date.sql` example makes this concrete and correct: the column is added **NULLABLE**, so code that predates it keeps inserting, and the contract (drop old shape) is a *later* separate forward migration only after every reader moved. That is the right shape. My "bad deploy" scar is answered not by "you can undo it" but by "you built it so it can't strand you" — which is a better answer, because it's the one that's actually true on a shared store.
- **The idempotent journal makes "re-run the last good deployment" safe for schema too** — which is the load-bearing claim that lets DB delivery use the *same* rollback action as everything else. `Program.cs:30-33` (`WithScriptsEmbeddedInAssembly` + the `SchemaVersions` journal) and the local-playground "run it twice, second run applies nothing" demo (`db-migrations/README.md:63`) close that loop honestly. The `MERGE`-based reference-data script (`Script0003`) extends idempotency to *data*, not just structure — which is the subtle part most shops get wrong, and they got it right.
- **The two genuinely scary shared-DB hazards are named and worked, not dodged.** Drift between environments (`database-delivery.md:34-42`): baseline prod as truth, `MarkAsExecuted`, reconcile lower envs *up* to prod — that is the correct and only-sane convergence order, and it answers my "you can't automate on top of unknown state" objection in its own words (`:36`). Cross-database references (`database-delivery.md:44-50`): version each DB independently, add no *new* cross-DB coupling, cross the boundary with expand/contract + ordered deploys. For an estate that is "one large database plus smaller ones that hold references across the boundary," that is the real problem named precisely.
- **The honesty about where we are is what actually sells it.** `database-delivery.md:32` concedes lower environments have drifted, there is no schema automation today, and local databases are uncommon — then assigns the path to DX as *direction*, not a team checklist. The CLAUDE.md framing (end-state owned by DX, not a rollout we're each graded on) shows up consistently in the assessment callout too (`current-state-assessment.md:50`: "that is a deliberate target DX is driving toward automation — note it, don't score it as a personal gap"). A skeptic reads "ship schema daily to shared prod" as a mandate to be afraid of; framing it as a *destination DX is building the road to* is what lowers the temperature enough to engage.

Where it does **not** fully convince me (and where it's thin):

- **It bounds my worst fear; it doesn't eliminate it, and it could say so more plainly.** Expand/contract makes the *backward-compatible* schema change safe to deploy daily. It says nothing reassuring about the change that *can't* be made backward-compatible cheaply — a type narrowing, a NOT-NULL backfill on a 50M-row table, a unique constraint that turns out to be violated by existing data. The course's answer is implicitly "decompose it into backward-compatible steps," same as it answers everything, and for schema that's often a *multi-week* expand-migrate-contract dance with a backfill in the middle. `strangler-fig-violations.md` works exactly that kind of long ordered backfill for *application data* — but `database-delivery.md` never works a single hard schema change end-to-end the way the README's `Script0002` only shows the *easy* expand (add a nullable column). The hardest case — a large-table backfill that locks, run forward-only through a pipeline, with the "what if the backfill itself fails halfway against shared prod" answer — is named in the abstract (`watermark` is even in the glossary) but never worked. **That's the thin spot.** For a skeptic, "add a nullable column" is the case I was never scared of. Show me the NOT-NULL-backfill-on-a-big-table case run forward-only and I'd give this a 10 on the DB axis alone.
- **"A red migration stops the line" against a shared `qa` is asserted, not de-risked.** `db-migrations.gitlab-ci.yml` proves migrations against an *ephemeral* SQL Server (`validate:migrations`, `:39`) — good, that's a production-like test (#7) for schema. But the leap from "applies cleanly against an empty ephemeral DB" to "applies cleanly against drifted shared `qa`/`prod` with real data and real constraints" is the entire risk, and the ephemeral test can't catch it. The drift section says "converge first," but the pipeline example doesn't show the data-shaped failure (a backfill that violates a constraint only *prod's* data trips). This is adjacent to Dana's carried R3-8/R6-D1 (prod-like *data* never worked) — and from my chair it's the same gap wearing a schema hat. Defensible as 201-scope; worth naming as the known frontier.

Net: this is the strongest thing the course could have done to my stance. I came in certain that shared-DB daily delivery was where trunk-based chaos cashes out, and I'm leaving thinking "expand/contract + forward-only is a disciplined answer I'd actually run" — with one honest reservation about the genuinely-hard schema change, which the course bounds but doesn't yet work.

### Theme 2 — CI / TBD / branch by abstraction

**Branch by abstraction: real engineering, sufficient — thin only in that it's defined, not worked.**

- The glossary entry (`resources/glossary.md:103`) is the test of whether this is hand-waving to prop up trunk-based, and it passes. It draws the distinction I'd draw: "Like a feature flag it lets you integrate before the work is finished — but it gates an *implementation* behind an interface, where a flag gates a *behavior* at a call site." That is exactly right, and it's the sentence that answers my standing objection. My Round-1/2 complaint was that decomposing a *structural* change (swap a data-access layer, replace a dependency) generated a pile of interacting flags. Branch by abstraction is the honest answer: you don't flag a refactor at N call sites, you put *one* seam over it and swap the implementation behind it. That genuinely beats keeping a long branch for a big refactor — because the seam lets the half-built new implementation live on trunk, integrated daily, behind a stable interface, instead of drifting on a two-week branch. I'm convinced of the *technique*.
- The Session 2 note (`sessions/session-2/README.md:92`) places it correctly: "some work is *structural* ... a large refactor a single switch can't cleanly wrap. There the technique is branch by abstraction." It names the seam, the build-behind, the caller migration, the delete-old-path. That's the whole move, accurately.
- The minimums-reference TBD section now treats long-lived branches as something *resisted by engineering technique*, not merely avoided by policy (`minimums-reference.md:63`, `:74`): "chiefly feature flags, with branch by abstraction for larger structural changes a call-site switch can't cleanly wrap." Good — it positions the two techniques by the shape of the work, not as interchangeable.
- The rewritten TBD glossary entry (`glossary.md:22`) is sharper than Round 2: "long-lived branches deliberately *resisted*, not merely avoided ... the discipline is the point, not the mechanism," and it correctly distinguishes TBD (source-control model) from CI (adds verification + stop-the-line) — "on its own ... it is not yet CI." That's a precise line a lot of shops blur, and getting it right earns trust.

**Thin spot:** branch by abstraction is *defined well but never worked.* The course's whole credibility-with-skeptics move in Round 2 was "we don't just assert it, we work the hard case" (`strangler-fig-violations.md`). Branch by abstraction gets a glossary entry and a paragraph, but no worked example showing the seam interface, the two implementations coexisting on trunk, and the caller-by-caller cutover for a real RealManage refactor. For the technique that's *supposed* to replace my favorite use of a long branch (the big internal refactor), "trust me, put an interface over it" is one tier below the standard the strangler-fig example set. It's enough to convince me the technique is sound; it's not enough to hand a junior and say "go." If I were prioritizing, a 30-line worked branch-by-abstraction (swap the Violations persistence layer behind an `IViolationStore` seam, old + new behind it, migrate callers, delete old) would bring this to the same bar as everything around it.

The rollback correction and the DB material reinforce each other instead of contradicting — which is how I know the sweep was done deliberately, not piecemeal.

## Factual / technical concerns

- **NEW DEFECT — the DB-migrations pipeline `needs:` chain breaks "build once, promote the same bytes."** `db-migrations.gitlab-ci.yml`: `build:migrator` (`:54`) produces the `publish/` artifact. `migrate:dev` (`:77`) correctly does `needs: [validate:migrations, build:migrator]`, so it receives `publish/`. But `migrate:qa` (`:84`) has `needs: [migrate:dev]` and `migrate:prod` (`:91`) has `needs: [migrate:qa]` — **neither lists `build:migrator`.** By GitLab's `needs:` artifact semantics, a job receives artifacts only from the jobs it lists in `needs:` (with `artifacts: true`, the default). `migrate:dev` produces no artifact. So `migrate:qa` and `migrate:prod` run `dotnet publish/Migrator.dll` against a `publish/` directory that **isn't there** — the job would fail at runtime, *or*, if someone "fixes" it by adding a `dotnet publish` to the `.migrate` script, you'd be **rebuilding per environment**, which is the exact immutability violation (#5) this whole example exists to teach against. This is the same class of bug Jordan/Riley caught in the app pipeline's `needs:` list in Round 2, now reappearing in the new DB file. Fix: add `build:migrator` (and carry its artifact) to the `needs:` of `migrate:qa` and `migrate:prod`, or have all three migrate jobs `needs: [build:migrator, <prior stage>]`. For a course whose headline DB claim is "the SAME publish/ artifact" promoted unchanged (`db-migrations/README.md:20-35`), the worked YAML must actually carry the same artifact forward. **This is my one real technical finding and the main reason this isn't a 10.**
- **The DbUp "same bytes" claim is otherwise correct.** `Migrator.csproj:19` (`<EmbeddedResource Include="Scripts\*.sql" />`) + `Program.cs:33` (`WithScriptsEmbeddedInAssembly`) genuinely make the scripts travel inside the published assembly, so the "scripts embedded in the DLL" diagram (`db-migrations/README.md:22-33`) is accurate, not aspirational. Connection-string-from-Secrets-Manager-via-OIDC-at-deploy-time (`:35`, YAML `:72-74`) is the right "config travels, secrets don't bake in" pattern. No complaint on the mechanism — only on the `needs:` wiring above.
- **`EnsureDatabase.For.SqlDatabase` against a *shared* prod is worth a caveat.** `Program.cs:25` calls `EnsureDatabase` — fine for a fresh local playground (which the comment says), but on a shared environment the database already exists and the migrator's role is schema-only; the runner having CREATE-DATABASE-implying rights against prod slightly cuts against the "least privilege, no standing DDL" spirit the DB guide preaches. Minor; the comment scopes it to "convenient for a fresh local DB," so it's flagged honestly — but a one-liner that this step is a local-convenience no-op on shared envs (where the DB is provisioned by IaC, not the migrator) would tidy the least-privilege story.
- **Round-2 technical items: no regressions.** Spot-checked the smoke test contract (`smoke-test.sh:48-55` asserts 400/501 = healthy, everything else fails — exactly the side-effect-free probe I asked for), the OIDC web-identity pattern (now also correctly used in the DB pipeline, `db-migrations.gitlab-ci.yml:27-35`), and the rollback-via-GitLab framing. All intact or improved.

## Persona-specific: the burned-by-a-bad-deploy engineer, on schema

My scar is a bad deploy. The course finally aimed the *scariest* version of that — a bad **schema** deploy to a **shared** database — straight at me, and here's how it landed:

- **What reassures:** the blast radius is bounded *by construction*, not by hoping you can undo it. Every step backward-compatible means the app rolls back without the schema rolling back; forward-only means you never face the "down-migration corrupted shared data" disaster I actually fear; the idempotent journal means the recovery action (re-run last good deploy) can't double-apply. That is a genuinely better safety model than the weekly-release "big batch, hope the rollback script works" world I came from — *for the changes that fit expand/contract.*
- **What still keeps me up:** the change that *doesn't* fit expand/contract cheaply (big-table backfill, constraint that prod data violates). The course's honest answer is "decompose and go forward-only," which I believe — but it's the unworked case, and it's the case bad-deploy scars are made of. The course bounds it; it doesn't yet rehearse it. I'd want the "rehearse it in qa" discipline (`rollback-on-aws.md:92`) explicitly extended to "rehearse a *migration* recovery against prod-like data," which is today only implied.

So: it talked to the scar this round, on the hardest terrain, and mostly held. That's worth a lot from where I sit.

## Recommendations

### High priority

- **Fix the DB-migrations `needs:` chain** (`db-migrations.gitlab-ci.yml:84`, `:91`) so `migrate:qa` and `migrate:prod` receive the `build:migrator` artifact and "promote the same bytes" is actually true in the YAML, not just the prose diagram. This is a real defect in the single example whose entire job is to teach build-once-promote for schema.

### Medium priority

- **Work one genuinely hard schema change end-to-end** — a NOT-NULL backfill on a large table, forward-only, expand→backfill(watermark/resumable)→contract, with the "backfill fails halfway against shared prod" answer. `database-delivery.md` names every piece (`watermark` is even glossed) but only `Script0002`'s trivial nullable-add is worked. This is the case that converts a DB skeptic the rest of the way.
- **Work a branch-by-abstraction example** (e.g., swap the Violations persistence behind an `IViolationStore` seam, old + new behind it, migrate callers, delete old). The technique is the designated replacement for my favorite use of a long branch — the big refactor — and it's the one major technique the course defines but never demonstrates to the standard `strangler-fig-violations.md` set.

### Nice to have

- One sentence in `database-delivery.md` / the DB pipeline noting the ephemeral `validate:migrations` proves *ordering and syntax*, not *prod's data* — so the drift/data risk is owned rather than implied (adjacent to Dana's R6-D1).
- A one-liner clarifying `EnsureDatabase` is a local-convenience no-op on shared envs (provisioned by IaC), to keep the least-privilege/no-standing-DDL story airtight.
- Extend "rehearse rollback in qa" explicitly to "rehearse a *migration* recovery," so the burned engineer sees schema recovery as a drilled capability, not a hope.
